# Слой — интернет-магазин кондитерских изделий

Полноценное демонстрационное приложение: современный адаптивный storefront, каталог с быстрым поиском и фасетами, иерархия «производитель → бренд → серия → товар», подборки, избранное, корзина для больших заказов и предпросмотр и подтверждение повторного заказа. Backend написан на Go в стиле чистой архитектуры; рабочее хранилище — PostgreSQL, а для быстрого локального просмотра есть in-memory режим.

## Что реализовано

- каталог с категориями и подкатегориями, производителями, брендами, сериями, тегами, ценой, наличием, сортировкой и пагинацией;
- подсказки поиска по товару, артикулу, производителю и бренду;
- редакционные подборки, карточка товара и группировка по производителям;
- авторизованные корзина, избранное, история заказов и оформление заказа;
- массовое выделение позиций и группировка большой корзины по производителям;
- предварительный просмотр повторного заказа: можно исключить позиции, изменить количество, увидеть дефицит, снятые товары, уже лежащий в корзине объём и изменение цены;
- атомарное добавление подтверждённых позиций повторного заказа;
- JSON-логи, request ID, security headers, ограничение JSON-body и graceful shutdown;
- PostgreSQL-миграции и воспроизводимые демоданные.

Демо-пользователь доступен в обоих backend-режимах:

```text
Email:    demo@sugar.ru
Пароль:   Sweet2026!
```

## Быстрый запуск через Docker Compose

Понадобятся Docker Engine и Docker Compose v2.

```bash
cp .env.example .env
docker compose config --quiet
docker compose up --build -d
docker compose ps
curl --fail http://127.0.0.1:8080/api/health
```

После запуска откройте <http://127.0.0.1:8080>: витрину `/` обслуживает Next, включая вход
`/login`. Прежний legacy-storefront доступен по <http://127.0.0.1:8080/legacy/> только для
отката и как справочный образец (см. «Владение маршрутами, выкладка и откат»). PostgreSQL и HTTP по умолчанию опубликованы только на loopback-интерфейсе. Для доступа снаружи задайте `APP_BIND=0.0.0.0`, но в production рекомендуется оставить приложение за TLS reverse proxy.

Логи и остановка:

```bash
docker compose logs -f app postgres
docker compose down
```

Именованный volume `postgres_data` сохраняется после `down`. Команда `docker compose down -v` необратимо удалит локальную базу и потребует повторной инициализации.

Перед публичным запуском обязательно замените `POSTGRES_PASSWORD` и ту же часть пароля в `DATABASE_URL`. Спецсимволы в URL-креденшалах должны быть percent-encoded.

## Локальный запуск без Docker

Требуется Go 1.22 или новее.

### Next storefront: локальная разработка и production-сборка

Первая frontend-основа находится в `apps/storefront` и запускается отдельно от Go-приложения.
Для неё нужен Node.js 22.12 или новее. Установка и запуск:

```bash
cd apps/storefront
npm ci
npm run dev
```

В разработке витрина доступна на <http://127.0.0.1:3000>; Go API и legacy-storefront из `web/`
работают отдельно на <http://127.0.0.1:8080>. В production-топологии Next владеет `/` за
edge. В витрине подключены маршруты `/` (главная),
`/catalog`, `/categories`, `/categories/:slug`, `/products/:slug`, `/manufacturers`,
`/manufacturers/:slug`, `/collections` и `/collections/:slug`, а также авторизованные
избранное `/favorites`, корзина `/cart`, оформление `/checkout` и подтверждение заказа
`/account/orders/:id`, история `/account/orders` и аккаунт `/account`.

Чтобы запустить Go API и Next storefront вместе, откройте два терминала из корня репозитория:

```bash
# Терминал 1: действующий Go API с временными демоданными
make run-memory

# Терминал 2: изолированная Next-витрина
cd apps/storefront
cp .env.example .env.local
npm ci
npm run dev
```

После этого реальный демотовар доступен, например, по адресу
<http://127.0.0.1:3000/products/dark-chocolate-sea-salt>. Go остаётся источником названия,
цен, наличия, правил количества, описания, атрибутов и изображений. Next также переписывает
текущие относительные `/assets/*` на настроенный Go origin, чтобы существующие изображения
работали в изолированной локальной разработке.

`STOREFRONT_API_BASE_URL` — server-side origin Go API. В локальной development-среде без
переменной используется `http://127.0.0.1:8080`. Для product и catalog API-запросов в production
переменная обязательна: без неё server-side transport возвращает понятную ошибку и никогда не
обращается к localhost. Сама production-сборка не требует доступного или настроенного backend;
если переменная при сборке отсутствует, `/assets/*` rewrite на localhost не создаётся. Пример
локальной настройки находится в `apps/storefront/.env.example`. Переменная намеренно не имеет
префикса `NEXT_PUBLIC_` и не предназначена для browser-кода. При изменении значения
перезапустите Next dev server.

Для production-like проверки используется один публичный edge origin. `docker compose --env-file .env.example up --build`
поднимает edge, в котором Next владеет `/` и всеми прочими путями (включая собственную 404),
а `/api/*`, `/assets/*` и legacy-storefront `/legacy` остаются за Go. Проверить ownership и
healthchecks можно так:

```bash
docker compose --env-file .env.example up --build --wait edge
bash scripts/test-edge-routes.sh
```

Production-образ Next собирается без basePath: маршруты и assets — это `/`, `/catalog`,
`/products/...`, `/_next/...`, healthcheck — `/healthz`. Прежний preview-путь
`/storefront-preview` удалён и отвечает 404 Next. `STOREFRONT_API_BASE_URL=http://app:8080` —
только внутренний server-to-server адрес Next → Go. Он не передаётся в browser JavaScript:
браузер всегда вызывает текущий origin по `/api`. Для публичного запуска TLS завершается перед
edge; укажите exact HTTPS public origin в `TRUSTED_ORIGINS` и включите secure cookie согласно
production-конфигурации Go: тот же origin нужен для входа на `/login`. Edge также отдаёт
legacy-приложение по `/legacy` и `/legacy/*` (префикс снимается, Go получает обычный путь), а
shell-файлы `/app.js`, `/migration.js`, `/styles.css` направляет в Go: на них ссылается
legacy-страница. Это только откат и справочный образец: ни одна обычная страница Next на
`/legacy` не ссылается. Выкладка и откат описаны в разделе «Владение маршрутами, выкладка и откат».

Структура текущего frontend-среза:

```text
apps/storefront/
  src/app/                 App Router, layout, главная, catalog, discovery и product routes
  src/components/ui/       доступные базовые примитивы
  src/components/storefront/  композиционные элементы витрины
  src/lib/api/             server-side конфигурация, transport и проверка DTO
  src/styles/              семантические tokens и небольшой global foundation
  src/test/                общая настройка компонентных тестов
```

Токены охватывают тёплые нейтральные цвета, типографику, интервалы, радиусы, границы,
ограниченную elevation, motion, responsive-контейнеры, focus, density и z-index. Реализованы
`Button`, `IconButton`, `TextInput`, `SearchInput`, `Badge`, `QuantityControl`, `Container`,
визуально скрытый текст и индикатор загрузки. Сторонняя UI-библиотека не используется.

Проверки frontend:

```bash
cd apps/storefront
npm run typecheck
npm run lint
npm test
npm run build
```

Product route использует текущий `GET /api/products/{product}`, который принимает ID, slug или
регистронезависимый SKU. Канонический Next URL использует возвращённый API slug; обращение по
ID/SKU перенаправляется на него. Запрос выполняется на сервере с `cache: no-store`, потому что
цена и остаток изменяемы. Ответ проверяется на typed boundary; 404 открывает отдельное
not-found состояние, а сетевой/серверный сбой — восстанавливаемое состояние с повтором.

Catalog route использует реальные `GET /api/catalog`, `/api/catalog/facets`, `/api/categories`,
`/api/manufacturers` и `/api/brands`. Состояние хранится в query string: `q`, `category`,
`manufacturer`, `brand`, `series`, повторяемый `tag`, рублёвые границы `min`/`max`, `stock`,
`sale`, `new`, `sort`, `page`, `size` и `view=compact`. UI передаёт цены backend в целых
minor units и использует только серверную пагинацию. Реализованы независимая категория,
цепочка «производитель → бренд → серия», характеристики, цена, наличие, сниженная цена,
новинки, сортировки по названию/дате/цене и размеры страницы 24/48/96. Будущие disjunctive
facet counts не имитируются: текущие facet-значения остаются полностью отфильтрованными.

Каталог имеет два представления: комфортные карточки для просмотра и компактные строки для
работы с большим числом SKU; на узком экране строки перекомпоновываются без горизонтальной
таблицы. Количество на product page управляет подтверждённой серверной корзиной для вошедшего пользователя.
Избранное работает через существующий Go API для вошедшего пользователя.

Producer navigation использует реальные справочники `GET /api/manufacturers` и `/api/brands`.
`/manufacturers` показывает локально фильтруемый алфавитный список, потому что текущий API
возвращает полный непагинированный справочник. `/manufacturers/:slug` разрешает уникальный slug
(или внутренний ID с перенаправлением на slug), показывает реальные бренды и ведёт в существующий
`/catalog` через точные `manufacturer` и `brand` query-параметры. Серии не загружаются заранее
для каждого бренда: они остаются свободным текстом и появляются как brand-scoped facets уже в
каталоге после выбора бренда. Канонических series routes нет. Отдельные brand pages, server-side
поиск/пагинация производителей и стабильные series entities намеренно отложены до расширения
backend-контракта.

Collection discovery использует реальный непагинированный `GET /api/collections`.
`/collections` показывает только возвращённые API название, описание, изображение и количество,
а `/collections/:slug` разрешает slug или внутренний ID с перенаправлением на канонический slug.
Первые четыре товара загружаются по упорядоченному `productIds` и показываются в редакционном
порядке; полный список открывается в существующем `/catalog?collection=<slug>` с серверной
пагинацией и сортировкой каталога. Пустой справочник и пустая подборка различаются.

Текущая видимость ограничена фактическим контрактом: PostgreSQL и memory показывают подборку,
когда `starts_at` не задан или уже наступил, и `ends_at` не задан или ещё не прошёл; обе границы
включительны. То же расписание применяется к прямому catalog filter, где невидимая или неизвестная
подборка даёт пустой результат. Статусов draft/published/archive нет. Полная lifecycle-модель,
отдельный detail endpoint и catalog-сортировка по редакционному
`collection_products.sort_order` отложены до backend-расширения.

Category navigation использует реальный непагинированный `GET /api/categories`: API возвращает
полный плоский справочник, а дерево строится в storefront по `parentId`. Построение защищено от
повторных ID, неизвестных родителей (становятся корневыми) и циклов (каждая категория выводится
ровно один раз). `/categories` показывает корневые категории с прямыми подкатегориями (не больше
восьми, дальше — ссылка на страницу категории); `/categories/:slug` разрешает slug или внутренний
ID с перенаправлением на канонический slug, показывает хлебные крошки по предкам, подкатегории
или соседние категории и ведёт в существующий `/catalog?category=<slug>`. Собственного списка
товаров у страниц категорий нет. `/catalog` использует то же дерево для активной корневой
категории, отступов в списке и хлебных крошек.

Текущая семантика backend одинакова в PostgreSQL и memory: фильтр `category` и `productCount`
включают саму категорию и только её прямые подкатегории, без рекурсивных потомков. Поэтому
количество подписывается нейтрально («N товаров в каталоге») и совпадает с результатом
нефильтрованного `/catalog?category=<slug>`, а storefront не суммирует счётчики по дереву.
Рекурсивные потомки, защита от циклов и индекс по `parent_id` в базе, detail endpoint категории,
меню каталога в шапке и мобильная навигация по уровням отложены; рекурсия обязательна до
появления таксономии глубже двух уровней.

Глобальный поиск в шапке — доступный combobox поверх существующего `GET /api/search/suggest`.
Браузер обращается к same-origin route handler `apps/storefront/src/app/api/search/suggest`,
который повторяет путь, статусы и конверты Go: запрос короче двух символов даёт `{items: []}`
без обращения к API, длиннее 200 Unicode code points — тот же `422 validation_error`, что и Go;
сбой upstream — `502` с конвертом `internal_error`. Базовый URL API остаётся server-only.
Подсказки запрашиваются с debounce 160 мс, устаревшие запросы отменяются, а поздние ответы
отбрасываются по номеру запроса. Стрелки, Enter, Escape и Tab работают по схеме combobox,
активный вариант объявляется через `aria-activedescendant`, `Ctrl/Cmd+K` фокусирует видимое
поле. Enter без выбранного варианта и последний пункт ведут на канонический `/catalog?q=…`;
`/search?q=…` временно (307) перенаправляет туда же. Без JavaScript форма отправляется в `/catalog`.

Подсказки показывают только то, что возвращает backend: товары, затем категории, производители
и бренды, если после товаров осталось место из восьми. Серий, подборок, артикула и цены в
подсказках нет; бренд ведёт в `/catalog?brand=<slug>`, потому что brand route отсутствует.
Ранжирования по релевантности нет: сортировка результатов с `q` совпадает с обычной сортировкой
каталога (в PostgreSQL последним ключом добавлен `p.id` для детерминированных страниц). Поиск
не нормализует `ё/е` («темный» не находит «Тёмный»), пунктуацию SKU и морфологию; `%` и `_`
в PostgreSQL сохраняют смысл LIKE-шаблонов. Регистр кириллицы сворачивается только в базе с
UTF-8 `LC_CTYPE`: в кластере интеграционных тестов (`initdb --no-locale`, C ctype) `lower()` и
`simple` full text не меняют регистр кириллицы, поэтому регистронезависимость для русских запросов
там не проверяется. Типизированные квоты подсказок, серии/подборки, релевантность, опечатки,
отдельная страница `/search`, полноэкранный мобильный поиск и недавние запросы отложены.

Главная (`apps/storefront/src/app/(home)`) — server-rendered маршрут без собственного client
state. Она строится только из текущих API и не больше чем из семи backend-запросов: параллельно
`GET /api/categories`, `/api/collections` и `/api/manufacturers`, затем параллельно до четырёх
`GET /api/products/{id}` для выбранной подборки. Каталог целиком, facets и brands не
загружаются. Разделы сверху вниз:

- вступление: фактический заголовок и одна фраза о поиске по названию, артикулу, производителю и
  бренду, ссылка «Открыть каталог», ссылка на выбранную подборку (если есть) и декоративная
  фотография `/assets/hero-confectionery.webp` из legacy-ассетов через существующий rewrite;
- категории: корневые категории в порядке ответа API, не больше восьми, с нейтральным счётчиком
  «N товаров в каталоге» и ссылками на `/categories/:slug`;
- подборка: первая подборка **в порядке текущего ответа** `/api/collections`, у которой есть хотя
  бы один `productId`. Видимость по расписанию уже применена в Go; Next не проверяет даты и не
  сортирует подборки. Это правило главной, а не гарантия API: PostgreSQL сейчас сортирует по
  `sort_order, name`, memory — в порядке фикстур. Показываются первые четыре товара в порядке
  `productIds` (тот же код, что у `/collections/:slug`), ссылки на ещё до трёх подборок и на
  `/collections`;
- производители: до восьми производителей с товарами по алфавиту (как в `/manufacturers`, латиница
  перед кириллицей), с ссылками на `/manufacturers/:slug`;
- навигация по разделам: каталог, категории, производители, подборки.

Разделы независимы (`Promise.allSettled`): сбой или пустой ответ убирает только свой раздел;
товар подборки, вернувший ошибку, убирает раздел подборки. Если недоступны все три источника,
остаются вступление, поиск в шапке, ссылки и короткое сообщение `role="status"`. Фикстуры и
заглушки не подставляются. Пустое или не загрузившееся изображение товара (в том числе упавшее
до гидратации) заменяется нейтральным полем «Нет фото» во всех карточках витрины. У backend нет документированных сигналов популярности, «избранных» или
рекомендованных товаров: `sort=popular` — эвристика (`featured`, отзывы, рейтинг), поэтому
главная ничего не называет популярным, рекомендованным или хитом. Редакционные бейджи товаров и
названия подборок из API выводятся дословно, но никогда не используются для отбора. Отложены:
разделы новинок (`newOnly`) и скидок, рекомендации и персонализация, блок повторного заказа,
промо/CMS-контент и изображения подборок, изображения категорий и логотипы производителей,
глобальный footer с подтверждёнными контактами, фильтр каталога по `ids` (сократил бы четыре
запроса товаров до одного), кеширование главной и пагинированные справочники.

### Избранное в Next storefront

`/favorites` показывает реальные сохранённые товары вошедшего пользователя. Один ленивый
client provider обслуживает карточки главной, каталога (оба вида), подборок, страницу товара
и само избранное. Шапка содержит ссылки на desktop и mobile без глобального счётчика и не
загружает избранное ради навигации. Гостевое избранное, browser storage и merge-on-login
в этом срезе не реализованы; намерение добавить товар после входа не сохраняется и не повторяется.

Go владеет HttpOnly cookie-сессией. Браузер сначала вызывает same-origin `GET /api/auth/session`,
затем, только при подтверждённом входе, `GET /api/favorites`. Проверку сессии избранное и корзина
делят через общий browser-session слой (статус, ID пользователя, CSRF в памяти, поколение);
снимки, мутации и сообщения каждой функции остаются отдельными. CSRF передаётся
в `X-CSRF-Token` для изменений; cookie и CSRF не попадают в server-rendered props.
В development `/api/*` использует существующий fallback rewrite, в production маршрутизацию
в Go обеспечивает внешний edge. Ошибка проверки сессии отображается как недоступность,
а не как выход. Каждый снимок избранного привязан к ID пользователя; смена пользователя,
выход или недоступность проверки скрывает прежние приватные данные и инвалидирует поздние ответы.

Изменения не оптимистические: сердечко и список меняются после ответа Go. На весь provider
допускается одна мутация, её полный ответ заменяет снимок. `401` завершает локальное состояние
входа. `403 csrf_failed` вызывает проверку сессии и перечитывание списка без повтора мутации.
После сетевой ошибки, `5xx` или повреждённого успешного ответа выполняется только GET-сверка:
запись могла успеть сохраниться. При неудачной сверке дальнейшие изменения блокируются до
восстановления. Возврат к скрытой/восстановленной вкладке вызывает ограниченную проверку;
синхронизации вкладок в реальном времени нет.

**Вход.** Вход — страница Next `/login`; отдельного backend-контракта у неё нет. Форма один раз
отправляет `POST /api/auth/session` с `{"email","password"}` на текущий origin
(`credentials: same-origin`, `no-store`, таймаут, без автоматического повтора). Go проверяет
`Origin` по `TRUSTED_ORIGINS`, ставит HttpOnly cookie сессии и возвращает `user` и `csrfToken`.
Ответ лишь подтверждает вход: `csrfToken` из него не сохраняется ни в storage, ни в cookie, URL,
логах или React context. После успеха форма делает полную навигацию `location.replace` на
целевой путь, поэтому все анонимные состояния сессии, корзины и избранного сбрасываются вместе с
документом; следующая страница читает сессию и свой CSRF-токен заново.

Ошибки: `401` — «Неверный email или пароль» (так же для выключенного демо-аккаунта), `422` —
сообщения Go у полей, `403 csrf_failed` — «Не удалось войти: обновите страницу», сеть, таймаут,
`5xx` и повреждённый ответ — «Сервис входа недоступен, попробуйте позже». Детали ответа backend не
показываются. Пока запрос идёт, кнопка заблокирована и повторная отправка невозможна.

Серверная часть `/login` динамическая и закрыта от индексации. Если Go подтверждает сессию,
страница сразу делает серверный redirect на целевой путь, не показывая форму. При недоступной
проверке сессии форма показывается с нейтральным уведомлением. Подсказка с демо-аккаунтом видна,
только если `GET /api/auth/session` явно сообщает `demoLogin: true`; поля никогда не
заполняются автоматически.

Ссылка «Войти» на приватных страницах Next (кнопки корзины и избранного в карточках и на
странице товара, избранное, корзина, оформление, аккаунт, история, заказ, повтор заказа) ведёт на
`/login?returnTo=<текущий путь>`, например `/checkout` → `/login?returnTo=%2Fcheckout`.
`returnTo` — путь приложения (без basePath: его добавляют ссылка Next и redirect, а форма —
перед навигацией) вместе с query и hash. Токены, CSRF и идентификатор пользователя в URL не
попадают. Настраиваемого URL входа больше нет.

Сервер принимает ровно одно значение `returnTo` и нормализует его; в браузер попадает только
нормализованный путь, сырой `returnTo` клиент не использует. Повторённый или недопустимый
`returnTo` заменяется на `/`. Допускаются только same-origin пути, начинающиеся с одного `/`, не
длиннее 2048 символов. Отклоняются:

- абсолютные и protocol-relative URL, а также `javascript:` и `data:`;
- обратный слэш, управляющие символы, повреждённое или двойное percent-кодирование;
- пути, которые после нормализации ведут к `//`;
- сегменты `legacy`, `login`, `auth`, `api`, `_next`;
- fragment `#/login` и `#/profile`;
- query-ключи `returnTo`, токенов, CSRF, пароля и user ID.

Правила одинаковы в `apps/storefront/src/lib/return-to.ts` и `web/migration.js` (вход legacy,
оставленный для отката) и проверяются общими тестовыми векторами.

Next также переводит старые закладки вида `#/…` (`LegacyHashBridge` в root layout) через
`router.replace`, с учётом basePath:

| Legacy hash | Next |
|---|---|
| `#/` и `#/home` | `/` |
| `#/catalog?…` | `/catalog` с совместимыми фильтрами |
| `#/favorites` | `/favorites` |
| `#/cart` | `/cart` |
| `#/orders` | `/account/orders` |
| `#/profile` | `/account` |
| `#/login` | `/login` |
| `#/delivery` | `/` (демо-страница не перенесена) |

Неизвестные hash и обычные якоря (`#main-content`) не трогаются. Так старые закладки вида
`/#/cart` после переключения root открывают соответствующую страницу Next.

При локальной работе Next dev server проксирует `/legacy/*` и shell-файлы legacy в Go только для
проверки отката; вход выполняется на `/login` самого Next.

Первый mount товарных controls (избранное и корзина вместе) делает один session GET для гостя
или три GET для вошедшего пользователя (session, favorites, cart) независимо от числа карточек.
Прямой авторизованный `/favorites` делает server session GET, browser session GET и favorites GET,
а при непустом списке карточки добавляют один cart GET; анонимный маршрут без cookie не обращается
к Go. Прямой авторизованный `/cart` — server session GET, browser session GET и cart GET.
Обычная успешная мутация — один запрос; CSRF recovery — ещё session GET и, при входе, favorites
GET; сверка неопределённого результата — один favorites GET. Данные товаров берутся из полного
`items` ответа избранного, без отдельных product/category/manufacturer-запросов. Наличие не
ограничивает сохранение. API пока непагинированный, дублирует товары в `groups` и не имеет
revision; bounded reads, batch actions, guest merge и полная миграция больших списков отложены.

### Корзина в Next storefront

`/cart` и кнопки покупки в карточках (главная, каталог в обоих видах, подборки, избранное) и на
странице товара работают только для вошедшего пользователя. Гостевой корзины, browser storage,
переноса legacy `sloy:cart` и merge после входа нет; намерение купить до входа не сохраняется.
Отдельный ленивый provider корзины использует общий browser-session слой. Шапка ведёт на `/cart`
без счётчика и не загружает корзину. Маршрут проверяет сессию через `getServerSession()` и
передаёт в браузер только статус и ID пользователя; гость видит предложение войти, сбой проверки —
состояние недоступности, а не пустую корзину. Страница закрыта от индексации.

Каждый защищённый ответ Go содержит `X-Authenticated-User-ID` — ID пользователя, авторизовавшего
именно этот запрос (ставится после аутентификации и CSRF до вызова обработчика, отсутствует
у `401` и `403 csrf_failed`, входящее значение игнорируется). Избранное и корзина принимают
приватный ответ, только если заголовок совпадает с ожидаемым пользователем запроса, а пользователь
и поколение запроса — с текущей сессией. Отсутствующий или чужой владелец: ответ отбрасывается,
приватные данные скрываются, выполняется одна общая проверка сессии без повтора мутации;
повторное несовпадение переводит состояние в «недоступно» до явной повторной загрузки.

Изменения не оптимистические, а Go — источник истины для сумм позиций, групп и итогов:
витрина их не пересчитывает и отклоняет небезопасные целые числа. Карточка добавляет
минимальное количество, страница товара — выбранное; `POST` и `PATCH` задают абсолютное
количество (не прибавку), `0` никогда не удаляет. Количество редактируется как черновик:
запись — по Enter, «Применить» или +/−, Escape возвращает подтверждённое значение. На весь
provider допускается одна запись: ответы содержат всю корзину без revision, поэтому параллельные
изменения даже разных товаров и скрытая очередь запрещены. Выбор всей корзины всегда отправляет
`PATCH /api/cart/selection` с явным непустым списком всех канонических ID (локальный поиск и
свёрнутые группы его не сужают); пустая корзина не отправляет запросов. Удаление — только
`DELETE /api/cart/items/{product}`; массового удаления нет. `409` сохраняет введённое количество
и перечитывает корзину, `422` сохраняет черновик без перечитывания, `401` скрывает корзину и
избранное, `403 csrf_failed` проверяет сессию и перечитывает данные без повтора. После сетевой
ошибки, `5xx`, повреждённого ответа или неожиданного статуса показывается последний
подтверждённый снимок с пометкой сверки и выполняется только `GET /api/cart`; при неудаче
изменения блокируются до явной повторной загрузки. Порядок позиций — порядок ответа Go
(не «недавние»); `updatedAt` не используется как revision.

Отложены: гостевая корзина и merge, счётчик в шапке, массовое удаление,
undo, фильтры выбранного/проблем, перенос в избранное, плотности, виртуализация и пагинация.

### Оформление заказа в Next storefront

`/checkout` доступен только вошедшему пользователю и открывается ссылкой «Перейти к оформлению» из
корзины, если выбрана хотя бы одна позиция и у выбранных нет проблем наличия. Ссылка ничего не
записывает. Маршрут, как и `/cart`, проверяет сессию на сервере и при входе заново читает корзину;
отдельного выбора для заказа нет — показываются только выбранные строки корзины, их цены и итоги Go
(«Товары без скидки», «Скидка», «Доставка», «Итого») и число невыбранных позиций, которые останутся в
корзине. Форма содержит только адрес доставки (обязателен) и необязательный комментарий, без
придуманных ограничений длины; имени, телефона, оплаты и интервала доставки нет.

Подтверждение — один `POST /api/orders` с `Idempotency-Key` (`crypto.randomUUID()`), CSRF,
`X-Expected-Authenticated-User-ID` и обзором (`expectedItems`, `expectedTotalMinor`), скопированным из
того же снимка корзины. Запрос держит общую блокировку записи корзины, таймаут — 20 секунд, повторов
нет. `409 checkout_changed`, `out_of_stock` и `conflict` перечитывают корзину, сохраняют форму, текстом
отмечают изменившиеся цены, количество и состав и требуют нового подтверждения с новым ключом; `422`
показывает ошибки полей; `403 csrf_failed` проверяет сессию и перечитывает корзину без повтора; `401`
завершает вход; чужой владелец ответа или `authenticated_user_changed` отбрасывают попытку.
При сетевой ошибке, таймауте, `5xx` или повреждённом `201` результат считается неизвестным: форма
блокируется, корзина не используется как доказательство, а кнопка «Проверить заказ» по явному
действию отправляет тот же запрос с тем же ключом — Go вернёт уже созданный заказ
(`Idempotent-Replayed`) или выполнит его один раз. Незавершённая попытка не сохраняется в браузере.

После `201` витрина переходит (`router.replace`) на `/account/orders/:id`. Страница читает
`GET /api/orders/{id}` с проверкой владельца и показывает номер, дату, статус Go, адрес, комментарий,
снимки позиций и «Итого с доставкой» — разбивки суммы у заказа в API нет. Плашка «Заказ … оформлен»
появляется только сразу после оформления в этой вкладке; после перезагрузки остаётся сам заказ.
Ссылки на товары используют ID из снимка (удалённый товар откроет 404). Каждый приватный запрос
браузера передаёт `X-Expected-Authenticated-User-ID`, поэтому Go отклоняет запрос устаревшей вкладки до
любых изменений. Повтор заказа доступен через `/account/orders/:id/repeat`;
гостевое оформление, оплата и отмена отложены.

### История заказов в Next storefront

`/account/orders` использует существующий непагинированный `GET /api/orders`: один ответ содержит
все заказы и их исторические позиции. Страница сохраняет порядок Go, показывает номер, дату из
ISO timestamp в локальном часовом поясе браузера, серверный статус, `itemCount` как число единиц,
итог и адрес доставки. Валюта заказа отсутствует в DTO; применяется та же договорённость RUB,
что и на странице заказа. Разбивка суммы и число позиций не вычисляются. История принимает
`items:null` внутри заказа и нормализует в пустой массив, сохраняя авторитетный `itemCount`;
строгий parser detail по-прежнему требует массив. Пагинации и «Загрузить ещё» нет:
неограниченный объём ответа остаётся долгом масштабирования backend.

Сервер передаёт только проверенный статус сессии, ID пользователя и ссылку входа. История
загружается в локальное состояние страницы через общий browser session и transport с
`X-Expected-Authenticated-User-ID`, проверкой владельца ответа и поколения сессии. При смене
аккаунта или проверке входа прежняя история сразу скрывается; поздние ответы отбрасываются.
`401` завершает локальную сессию, несовпадение владельца допускает одну проверку входа,
повторное несовпадение показывает недоступность. Ошибка не маскируется под пустую историю.

Холодный вход без cookie делает 0 запросов Go; авторизованный — server session GET,
browser session GET и ровно один orders GET. История не инициализирует Cart/Favorites и не
запрашивает отдельные товары или детали. Уже инициализированные приватные providers сохраняют
своё обычное перечитывание при обновлении общей сессии. Ссылки «Заказы» в desktop/mobile шапке,
ссылки на детали и «Все заказы» отключают prefetch. Обычное открытие исторического заказа не
создаёт плашку оформления: она по-прежнему зависит только от in-memory `placedOrder` handoff.
История и детали содержат ссылки на `/account/orders/:id/repeat`: Next review использует
strict Repeat v2, явное подтверждение, восстановление тем же ключом/телом и передачу
авторитетной Cart в `/cart`. Сам переход по ссылке ничего не добавляет.

Администрирование и окончательное production route ownership ещё не перенесены; страницы брендов,
серий и аккаунта уже доступны в Next storefront.

### In-memory demo mode

```bash
make run-memory
```

Или явно:

```bash
APP_MODE=demo DATABASE_URL= \
WEB_DIR=web \
MIGRATIONS_DIR=migrations \
go run ./cmd/server
```

Memory repository включается при пустом `DATABASE_URL` только с явным `APP_MODE=demo` или `APP_MODE=development`. По умолчанию действует `APP_MODE=production`: без PostgreSQL DSN сервер завершает запуск с ошибкой. Это удобный режим для интерфейса, API и тестирования сценариев, но все корзины, сессии и заказы исчезают при перезапуске процесса. Для нескольких реплик и любых сохраняемых данных он не подходит.

### PostgreSQL mode

Можно поднять только базу из Compose и запустить Go-процесс на хосте:

```bash
cp .env.example .env
docker compose up -d postgres

DATABASE_URL='postgres://sweetshop:LOCAL_PASSWORD@127.0.0.1:5432/sweetshop?sslmode=disable' \
RUN_MIGRATIONS=true \
WEB_DIR=web \
MIGRATIONS_DIR=migrations \
make run-postgres
```

Замените `LOCAL_PASSWORD` значением из вашего локального `.env`. Для подключения с хоста используйте `POSTGRES_PORT` (в `.env.example` и примере выше — 5432), а внутри Compose — `postgres:5432`.

В режимах `demo` и `development` приложение при старте создаст `schema_migrations`, применит все `*.up.sql` по номеру и загрузит демоданные. В `production` сервер миграции не применяет, а `shopctl migrate` создаёт схему без демоданных (см. «Миграции схемы» и «Демоданные и production»).

### Миграции схемы

Сервер, тесты и операторская команда `shopctl migrate` используют один движок
(`internal/repository/postgres/migrate.go`):

- миграция — файл `NNN_name.up.sql`; порядок задаёт номер. `*.down.sql` и не-SQL файлы
  игнорируются, любое другое имя `*.sql` и повтор номера — ошибка;
- запуск держит session-level advisory lock `MigrationLockKey` (`0x73776565746d6967`,
  «sweetmig») на отдельном соединении, изъятом из пула; соединение закрывается в конце,
  поэтому lock освобождается при успехе, ошибке и отмене. Второй мигратор ждёт lock,
  перечитывает состояние и ничего не применяет повторно;
- каждая миграция и её строка в `schema_migrations` фиксируются одной транзакцией с
  `SET LOCAL lock_timeout` (5 s по умолчанию): DDL не ждёт блокировку бесконечно;
- до выполнения любого SQL все файлы проверяются лексером, разбирающим комментарии, строки,
  `$tag$`-тела и `BEGIN ATOMIC` так же, как PostgreSQL/psql: файл с top-level `BEGIN`,
  `START`, `COMMIT`, `END`, `ROLLBACK`, `ABORT`, `SAVEPOINT`, `RELEASE` или
  `PREPARE TRANSACTION` отклоняется целиком, и запуск не выполняет ни одной миграции. Перед
  каждым файлом требуется `standard_conforming_strings = on`;
- в `schema_migrations` добавлены `checksum` (SHA-256 сырых байтов файла) и `outcome`
  (`applied` или `skipped`, ограничение `schema_migrations_outcome_allowed`). Колонки
  nullable/с default (`applied`), поэтому `INSERT INTO schema_migrations(version)` прежнего
  бинарника по-прежнему работает;
- строки 001–007, применённые до появления checksum, получают его один раз
  (`migration checksum adopted` в логе) и только если файл совпадает с закреплённым
  историческим SHA-256. Записанный checksum никогда не перезаписывается: несовпадение —
  жёсткая ошибка. Миграции 001–007 менять нельзя; `.gitattributes` запрещает Git
  конвертировать их переводы строк;
- известная миграция, пропущенная ниже уже применённой, — ошибка. Неизвестная версия
  выше всех известных (её записал более новый образ) допускается с предупреждением, чтобы
  можно было откатиться на предыдущий образ.

Перед стартом сервер в любом режиме выполняет read-only проверку схемы: все известные
миграции применены, checksums совпадают, пропусков нет. Иначе запуск завершается ошибкой
с подсказкой `shopctl migrate`. `RUN_MIGRATIONS` без значения означает: `production` только
проверяет, `demo`/`development` сначала применяют миграции. Только точные `true`/`false`
меняют это поведение; явное `true` в production применяет миграции при старте и пишет
предупреждение.

```bash
# Production (APP_MODE=production в .env): применить миграции одним запуском, затем стартовать сервер
docker compose run --rm --no-deps --entrypoint /app/shopctl app migrate
docker compose run --rm --no-deps --entrypoint /app/shopctl app migrate --status
```

`docker compose run ... app` наследует окружение сервиса `app`, включая `APP_MODE`
(`${APP_MODE:-production}`); образ без `APP_MODE` тоже работает как `production`.

#### Демоданные и production

Миграция `002_demo_seed` — единственная fixture-миграция: она загружает демо-аккаунт,
каталог, корзину, избранное и заказ и не меняет схему. Она явно перечислена в
`internal/repository/postgres/migrate.go` и, как 001–007, неизменяема. Что с ней делать,
определяет только `APP_MODE`; флага для переопределения нет:

| `APP_MODE` | Политика | `002_demo_seed` |
|---|---|---|
| `production` (по умолчанию) | skip | не выполняется; записывается `outcome=skipped` с checksum файла |
| `development`, `demo` | apply | выполняется; `outcome=applied` |

```bash
# Разработка: схема и демоданные
APP_MODE=demo shopctl migrate
# Production: та же схема с пустыми бизнес-таблицами
APP_MODE=production shopctl migrate
```

Записанный `outcome` — исторический факт и никогда не меняется. Production (skip) принимает
только `skipped`, разработка (apply) — только `applied`; противоречие — ошибка `migrate`,
`--status`, проверки при старте сервера. Если 002 нет, а более поздние миграции уже
записаны, это обычный пропуск (ошибка), а не `skipped`. Checksum пропущенной 002 тоже
проверяется: её файл нельзя изменить даже там, где она не выполнялась.

**База, в которой 002 была применена, не может стать production-базой.** Production-сервер и
`APP_MODE=production shopctl migrate` отказываются с ним работать и ничего не удаляют;
`shopctl migrate` эту ситуацию не исправляет. Для production создавайте новую пустую базу.
Не удаляйте демоданные вручную: проверенного способа очистки пока нет.

Откат на предыдущий образ после появления пропущенной 002:

- образ до этого движка миграций (`4556694` и раньше) проверяет только наличие строки версии,
  поэтому 002 не выполняет ни при `RUN_MIGRATIONS=false`, ни при прежнем автозапуске
  миграций; бизнес-таблицы остаются пустыми;
- образ `1748996` (первая версия этого движка) не знает `outcome=skipped` и отказывается
  стартовать на такой базе в любом режиме, ничего не меняя. Откатывайтесь на образ не старше
  текущего либо на образ до `1748996`, и всегда с `RUN_MIGRATIONS=false`.

`shopctl migrate` читает `DATABASE_URL`, `MIGRATIONS_DIR` и `APP_MODE`, пишет логи в stderr и
никогда не выводит DSN. Флаги: `--timeout` (по умолчанию 10m, включая ожидание lock),
`--lock-timeout` (5s), `--status` (только SELECT: без lock, bootstrap и SQL миграций; отчёт
в stdout). Коды выхода: 0 — успешно/актуально, 1 — сбой или несогласованная схема
(mismatch, пропуск, неизвестная версия), 2 — ошибка использования или конфигурации,
3 — `--status` нашёл незавершённую работу. После обновления существующей базы первый
`shopctl migrate` расширяет `schema_migrations` и записывает checksums; до этого
production-сервер не стартует.

### Учётные записи покупателей

В 1.0 регистрации нет: учётные записи создаёт оператор командой `shopctl customer`. Она
работает только с PostgreSQL, сначала выполняет ту же проверку схемы, что и сервер (база
должна быть мигрирована; в `production` — без демоданных), и лишь затем меняет данные.

```bash
# Пароль — одна строка в stdin; не аргумент и не переменная окружения.
# Терминал отклоняется, потому что показал бы ввод.
read -rs PASSWORD
printf '%s\n' "$PASSWORD" | docker compose run --rm --no-deps -T --entrypoint /app/shopctl app \
  customer create --email ann@example.com --name 'Анна Ли' --phone '+7 999 000-00-00' --password-stdin
unset PASSWORD

read -rs PASSWORD
printf '%s\n' "$PASSWORD" | docker compose run --rm --no-deps -T --entrypoint /app/shopctl app \
  customer set-password --email ann@example.com --password-stdin
unset PASSWORD

docker compose run --rm --no-deps --entrypoint /app/shopctl app customer disable --email ann@example.com
docker compose run --rm --no-deps --entrypoint /app/shopctl app customer enable --email ann@example.com
```

- email обрезается по краям и приводится к нижнему регистру; допускается только ASCII
  (международные домены — в punycode), поэтому совпадает с уникальным индексом
  `lower(email)` и с нормализацией при входе. Повтор email в любом регистре отклоняется;
- пароль: от 10 символов, не больше 72 байт UTF-8 (предел bcrypt; длиннее — отказ, а не
  обрезка), без управляющих символов и пробелов по краям. Хеш — bcrypt cost 12;
- имя обязательно (до 100 символов), телефон необязателен (цифры, пробелы, `+`, скобки,
  дефисы);
- `set-password`, `disable` и `enable` в одной транзакции отзывают все сессии учётной записи
  (cookie и bearer). Отключённая запись не может войти (ответ тот же, что при неверном
  пароле), а её сессии отклоняются, даже если появились в обход отзыва. Повторный
  `disable` сохраняет исходное время;
- вход связывает новую сессию с только что проверенным хешем и под блокировкой строки
  пользователя проверяет, что хеш не сменился и запись не отключена: вход со старым паролем,
  начатый до сброса, сессию не получит;
- результат — одна JSON-строка в stdout (`action`, `account`, `revokedSessions`); пароль и хеш
  никогда не выводятся. Коды выхода: 0 — успех, 1 — сбой или непригодная схема, 2 — ошибка
  аргументов или данных, 3 — email уже занят / такой записи нет.

Откат на образ до миграции `008_customer_account_status` (`3e19ff9` и раньше) не знает об
отключении: такие образы снова пускают отключённые записи. Сессии, отозванные при
отключении, не возвращаются, но после такого отката отключите запись повторно.

### Учётные записи сотрудников (staff)

Сотрудники — отдельный принципал: таблицы `staff_users`/`staff_sessions`, cookie
`__Host-sweetshop_staff` (SameSite=Strict; в разработке — `sweetshop_staff` без Secure), CSRF в
собственном пространстве, origin-ы `STAFF_TRUSTED_ORIGINS` и API `/api/admin/v1/*`
(контракт — `api/admin-openapi.yaml`). Ни cookie, ни bearer-токен покупателя не
аутентифицируют сотрудника, и наоборот. Решения и отклонения от ADR 006 (одна роль, MFA
отложена) — в [ADR 007](docs/adr/007-staff-identity.md).

```bash
read -rs PASSWORD
printf '%s\n' "$PASSWORD" | docker compose run --rm --no-deps -T --entrypoint /app/shopctl app \
  staff create --email ops@example.com --name 'Оператор' --password-stdin
unset PASSWORD
# staff set-password --email E --password-stdin | staff disable --email E | staff enable --email E
```

- пароль сотрудника — от 12 символов (остальные правила и вывод — как у `shopctl customer`);
- `set-password`, `disable` и `enable` в одной транзакции отзывают все сессии сотрудника;
  неизвестный email, неверный пароль и отключённая запись дают одинаковый 401;
- сессия — 12 часов без продления; вход всегда выдаёт новый токен и отзывает предъявленную
  staff-сессию; в БД хранится только SHA-256 токена;
- staff API регистрируется только при непустом `STAFF_TRUSTED_ORIGINS` и PostgreSQL; иначе
  `/api/admin/*` отвечает 404. Origin-ы — точные, https в production и не пересекаются с
  `TRUSTED_ORIGINS` (иначе сервер не стартует);
- магазинный edge сам отвечает 404 на `/api/admin` и `/api/admin/*` при любой настройке Go:
  админке нужен отдельный origin (ADR 006), он появится в следующих этапах. Ролей, MFA и
  audit-журнала пока нет.

### Выход из сессии: legacy и guarded mode

`DELETE /api/auth/session` без `X-Expected-Authenticated-User-ID` сохраняет прежний контракт:
bearer имеет приоритет и не затрагивает cookie; cookie требует trusted Origin и CSRF;
успешный cookie logout очищает cookie. Без credentials, а также при повторном выходе или
истёкшей сессии сохраняется `204` (для предъявленной cookie по-прежнему обязательна CSRF-проверка).

Наличие expected-user header, включая пустое значение, включает guarded mode для
logout в Next. Сначала выбирается тот же credential; для cookie проверяются Origin и CSRF,
затем Go аутентифицирует выбранный token/transport. Отсутствующая, неверная, истёкшая,
отозванная или запрещённая demo-сессия даёт `401 unauthorized` без владельца ответа.
После успешной аутентификации `X-Authenticated-User-ID` содержит **реального** владельца;
пустое, повторённое или несовпадающее expectation даёт `409 authenticated_user_changed`.
Отклонённый guarded logout (`401`, `403 csrf_failed`, `409`) ничего не отзывает и не очищает cookie.

При совпадении возвращается пустой `204` с owner header: отзывается только выбранная сессия,
cookie очищается только при cookie logout. Другие сессии того же пользователя и других
пользователей остаются действительными; logout-all не реализован. Все ответы — `no-store`;
ошибка хранилища после аутентификации сохраняет owner header. Bearer продолжает иметь
приоритет даже при одновременно предъявленной cookie другого пользователя.
Backend с guarded mode следует развернуть до Next logout. Legacy-клиенты без expected-user
header не требуют изменений.

Next `/account` — динамический маршрут с `noindex`, использующий серверную session gate и
существующий BrowserSessionProvider. Имя, email и непустой телефон проецируются из того же
проверенного browser session response, что user ID и CSRF, и публикуются вместе с generation.
Проверка сессии скрывает прежние поля; данные хранятся только в памяти. `/api/me` не вызывается.
Ссылки «Мои заказы», «Избранное», «Корзина» и «Аккаунт» в шапке имеют `prefetch={false}`.
Свежий авторизованный прямой переход требует два session GET (сервер + браузер), без чтений
корзины, избранного и заказов. Уже инициализированные private providers перечитываются при
подтверждении новой generation по прежним правилам.

Кнопка «Выйти» отправляет один guarded DELETE с текущими user ID и CSRF. Только пустой `204`
с правильным owner и всё ещё текущей generation переводит общую сессию в anonymous;
подписки скрывают private state, фокус переходит на сообщение о выходе, URL остаётся `/account`.
Все ошибки, включая `401`, `403`, `409`, неверный owner, timeout и сеть, запускают ровно одну
session reconciliation без повтора DELETE. Anonymous подтверждает выход, authenticated
показывает актуальный аккаунт и допускает новую явную попытку, unavailable сообщает о
неподтверждённом результате. Устаревшие результаты не изменяют новую сессию.
Редактирование профиля, пароля, адресов, регистрация и logout-all в Next не реализованы.

### Повтор заказа

Сначала frontend вызывает preview. Для демозаказа в PostgreSQL:

```bash
curl --fail --request POST \
  --header "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8080/api/orders/ord-2026-002/repeat/preview
```

Ответ показывает для каждой позиции заказанное, доступное и уже находящееся в корзине количество, текущую цену, статус `available`, `limited`, `unavailable` или `discontinued`, а также возможную замену. После редактирования отправляется точный выбор пользователя:

```bash
curl --fail --request POST \
  --header "Authorization: Bearer $TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"items":[
    {"productId":"p01","quantity":2,"selected":true},
    {"productId":"p07","quantity":4,"selected":true},
    {"productId":"p18","quantity":0,"selected":false}
  ]}' \
  http://127.0.0.1:8080/api/orders/ord-2026-002/repeat/commit
```

Backend заново строит preview перед commit, валидирует актуальный остаток, минимальное количество и шаг, затем применяет все изменения корзины одной операцией repository. Если `items` отсутствует, равен `null` или пуст, используются предложенные количества из нового preview. Это текущий legacy-контракт: обязательного предварительного review, фиксации цены и идемпотентности нет.

### Strict Repeat v2 (Checkpoint B)

Legacy v1 выше сохранён полностью, включая defaults для отсутствующего/null/пустого `items`.
V2 preview — чтение без записи review, TTL, резерва или receipt. Каждая строка имеет настоящий
`sourcePosition` из исторического заказа: одинаковый `productId` может встречаться несколько раз.
Preview содержит исторические SKU/имя/изображение/количество/цену, текущий `product` с ценой,
валютой, остатком, minimum/step, количество и selected в Cart, suggestions и статус.
Замена информационная; выбрать её через v2 пока нельзя. Suggestions рассчитаны по одной строке,
а одновременные добавления одинакового товара проверяются суммарно при commit.

Commit требует ровно один `Idempotency-Key` (`^[A-Za-z0-9_-]{16,128}$`) и непустой явный `items`:

```json
{"items":[{"sourcePosition":1,"productId":"p01","quantity":2,"expectedExistingCartQuantity":3,"expectedUnitPriceMinor":12900,"expectedCurrency":"RUB","expectedMinimumQuantity":1,"expectedQuantityStep":1}]}
```

Значения expectations берутся из свежего preview; пример не является текущими demo-ценами.
`quantity` — единицы **для добавления**; пропуск строки исключает её, `selected` не принимается.
Транзакция проверяет исходную строку, canonical ID и все expectations. Несовпадение —
`409 repeat_changed`, требуется новый preview и новое подтверждение. Stock не обязан быть равен
preview: он должен покрывать точное итоговое количество, иначе `409 out_of_stock`.
Добавления всех выбранных sourcePosition одного товара агрегируются; итог Cart должен
соответствовать minimum/step (иначе 422). Нет clamping, автоматической замены или retry.

Миграция `007_repeat_commits` хранит только успешные receipts и серверный digest `repeat/v2`.
Запись receipt и изменения Cart атомарны. Повтор с тем же пользователем/ключом/телом возвращает
`200`, `Idempotent-Replayed: true`, исходный `receipt` и **текущую полную Cart**, без нового
добавления. Receipt содержит source order ID/номер, число разных добавленных товаров,
сумму единиц и явные additions по sourcePosition. Иное тело с тем же ключом —
`409 idempotency_key_reused`. Проверка receipt предшествует проверке текущих expectations,
поэтому потерянный успешный ответ можно восстановить тем же запросом после изменения Cart.
Один Cart GET не доказывает успех. Срок истечения receipts не введён.

V2 использует общий cookie/bearer auth, cookie CSRF, `no-store` и expected-user/response-owner
контракт. Каждая PostgreSQL-транзакция изменения Cart сначала блокирует строку пользователя
`FOR NO KEY UPDATE` до commit/rollback, затем товары и Cart строки по canonical product ID.
Checkout проверяет весь выбранный набор без фильтра ранее захваченных IDs: изменения,
завершившиеся до user lock, видны проверке, более поздние записи того же пользователя ждут.
FK `KEY SHARE` остаётся совместимым; разные пользователи сохраняют независимость. Отдельный
advisory lock для Repeat key больше не нужен: receipt проверяется до входа и повторно под
user lock, всегда до проверки review. Memory сохраняет существующий mutex.
Полные DTO и ошибки — в `api/openapi.yaml`. Next Repeat UI реализован на
`/account/orders/:id/repeat`: preview, явный commit, восстановление неопределённого
результата тем же ключом/телом и передача возвращённой Cart в `/cart`.

### Оформление заказа: идемпотентность и проверка

`POST /api/orders` без новых полей работает как раньше и не идемпотентен. Новый клиент передаёт
заголовок `Idempotency-Key` (16–128 символов `A-Za-z0-9_-`, например `crypto.randomUUID()`) и
подтверждённый обзор: `expectedItems` (`productId`, `quantity`, `unitPriceMinor` выбранных строк) вместе
с `expectedTotalMinor`. Go в той же транзакции после блокировок сверяет точный набор выбранных строк,
количества, текущие цены и итог с доставкой; при расхождении — `409 checkout_changed` без записей.
Эти значения только сравниваются и никогда не определяют цену заказа.

Ключ и вычисленный сервером SHA-256-дайджест нормализованного запроса хранятся в созданном заказе
(уникальны в пределах пользователя). Повтор с тем же ключом и тем же запросом возвращает исходный заказ
с `201` и `Idempotent-Replayed: true` — даже когда корзина уже израсходована; тот же ключ с другим
запросом — `409 idempotency_key_reused`. Неудачные попытки ничего не сохраняют. Проверка минимального
количества и шага при оформлении по-прежнему не выполняется.

## Чистая архитектура

```text
cmd/server/                    composition root, конфигурация, HTTP lifecycle
internal/domain/               сущности, ошибки и интерфейс Repository
internal/application/          use cases и бизнес-валидация
internal/delivery/httpapi/     HTTP-маршруты, auth, JSON, middleware
internal/repository/memory/    временный демо-адаптер
internal/repository/postgres/  production-адаптер и runner миграций
migrations/                    версионированная схема и seed
web/                           статический frontend
```

Домен и application-слой не зависят от HTTP или PostgreSQL. `cmd/server` проверяет `APP_MODE`, выбирает adapter по наличию `DATABASE_URL` и связывает зависимости через интерфейс `domain.Repository`.

Каталог моделируется двумя дополняющими осями: дерево товарных категорий отвечает на вопрос «что это», а цепочка «производитель → бренд → серия → товар» — «кто и в какой линейке это выпустил». Подборки остаются независимыми many-to-many наборами товаров, поэтому навигация не разрастается в дублирующее дерево.

## Владение маршрутами, выкладка и откат

Публичный edge (`deploy/nginx/default.conf.template`):

| Путь | Владелец |
|---|---|
| `/edge/healthz` | edge |
| `/api`, `/api/*`, `/assets`, `/assets/*` | Go |
| `/legacy`, `/legacy/*` | Go legacy (только откат и справочный образец) |
| `/app.js`, `/migration.js`, `/styles.css` | Go (shell-файлы legacy-страницы) |
| `/_next/*` | Next |
| `/` и все остальные пути | Next, включая 404 |

`/legacy` остаётся доступным на весь период наблюдения после переключения как средство отката.
Обычные страницы Next на него не ссылаются: вход выполняется на `/login`.

Карта маршрутов выбирается переменной `EDGE_ROUTE_MAP`. Допустимы только два значения:
`default` (Next владеет `/`) и `legacy-root` (откат: `/` и неизвестные пути снова за Go legacy,
`deploy/nginx/legacy-root.conf.template`). Любое другое значение не даёт edge запуститься.
Откат меняет только маршрутизацию: без пересборки Go и Next, без миграций и без потери сессий,
корзин, избранного и заказов.

```bash
# Откат: Go legacy снова владеет /
# 1. В .env задайте EDGE_ROUTE_MAP=legacy-root, чтобы следующий `up` его не отменил.
docker compose up -d --no-deps --force-recreate edge
EXPECT_ROOT_OWNER=legacy EDGE_ORIGIN=https://<public-origin> bash scripts/test-edge-routes.sh

# Возврат к Next: в .env задайте EDGE_ROUTE_MAP=default, затем
docker compose up -d --no-deps --force-recreate edge
```

`--no-deps` обязателен: без него edge ждёт healthy `storefront` и не поднимется, если неисправен
сам Next.

Порядок выкладки (basePath компилируется при сборке, поэтому образ Next собирается до
переключения edge):

1. CI зелёный для коммита: `storefront`, `check`, `edge-routing`.
2. `git pull`, в `.env` задайте `EDGE_ROUTE_MAP=legacy-root`, проверьте свободное место
   (`df -h`) и выполните `docker compose build storefront`.
3. `docker compose up -d --no-deps storefront`. Запущенный edge продолжает работать по прежней
   карте, `/` остаётся за Go.
4. Проверьте healthcheck `storefront` (`docker compose ps`).
5. `docker compose up -d --no-deps --force-recreate edge` на карте `legacy-root`, затем
   `EXPECT_ROOT_OWNER=legacy EDGE_ORIGIN=https://<public-origin> bash scripts/test-edge-routes.sh`.
6. В `.env` задайте `EDGE_ROUTE_MAP=default`, снова пересоздайте только edge и выполните
   `EXPECT_ROOT_OWNER=next EDGE_ORIGIN=https://<public-origin> bash scripts/test-edge-routes.sh`.
7. Ручная проверка с отдельной тестовой учётной записью: вход через `/login` и возврат,
   аккаунт, выход, избранное и корзина с восстановлением состояния. Оформление и повтор заказа
   проверяйте только на staging: они создают реальные заказы.
8. Наблюдайте за 404 в access-логах edge и ошибками Next/Go. При проблеме выполните откат выше.

`scripts/test-release-flow.mjs` (headless Chrome + CDP) автоматически проходит вход, возврат,
избранное, корзину, оформление, историю и выход. Он создаёт заказ, поэтому запускается только в
CI и на одноразовых данных, не в production.

## Production checklist

`APP_MODE=production` закрывает только опасный fallback без базы. Миграция `002` по-прежнему добавляет демоаккаунт даже в production; этот этап не делает приложение готовым к публичным продажам. Если отслеживаемый ранее `.env` использовался в развёртывании, соответствующие учётные данные необходимо ротировать. Удаление из индекса не удаляет секреты из истории Git.

- замените демонстрационный пароль PostgreSQL; создавайте production-базу пустой через `APP_MODE=production shopctl migrate` (в ней нет `demo@sugar.ru` и демокаталога) и не используйте базу, где применялась `002_demo_seed`;
- передавайте секреты через secret manager платформы, не коммитьте `.env`;
- завершайте TLS на reverse proxy/load balancer, задайте ограничения request body и rate limits на внешнем контуре;
- не публикуйте порт PostgreSQL наружу; loopback-bind в Compose предназначен только для администрирования одного хоста;
- включите регулярные backup/PITR, мониторинг пула, диска и latency, а JSON-логи направьте в централизованное хранилище;
- применяйте миграции `shopctl migrate` до запуска новой версии; production-сервер по умолчанию их только проверяет. параллельные запуски сериализуются advisory lock;
- используйте PostgreSQL для нескольких реплик: memory mode неперсистентен и изолирован внутри процесса;
- проверяйте `/api/health` readiness-пробой и давайте процессу до 10 секунд на graceful shutdown;
- держите `EDGE_ROUTE_MAP` в `.env` явно и выкладывайте по порядку из раздела «Владение маршрутами, выкладка и откат»;
- образ уже запускается без root, а Compose дополнительно включает read-only root filesystem, `no-new-privileges` и удаляет Linux capabilities.
