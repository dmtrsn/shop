# Слой — интернет-магазин кондитерских изделий

Полноценное демонстрационное приложение: современный адаптивный storefront, каталог с быстрым поиском и фасетами, иерархия «производитель → бренд → серия → товар», подборки, избранное, корзина для больших заказов и предпросмотр и подтверждение повторного заказа. Backend написан на Go в стиле чистой архитектуры; рабочее хранилище — PostgreSQL, а для быстрого локального просмотра есть in-memory режим.

## Что реализовано

- каталог с категориями и подкатегориями, производителями, брендами, сериями, тегами, ценой, наличием, сортировкой и пагинацией;
- подсказки поиска по товару, артикулу, производителю и бренду;
- редакционные подборки, карточка товара и группировка по производителям;
- авторизованные корзина, избранное, история заказов и оформление заказа;
- массовое выделение позиций и группировка большой корзины по производителям;
- предварительный просмотр повторного заказа: можно исключить позиции, изменить количество, увидеть дефицит, снятые товары, уже лежащий в корзине объём и изменение цены;
- атомарное добавление подтверждённых позиций повторного заказа;
- JSON-логи, request ID, security headers, ограничение JSON-body и graceful shutdown;
- PostgreSQL-миграции и воспроизводимые демоданные.

Демо-пользователь доступен в обоих backend-режимах:

```text
Email:    demo@sugar.ru
Пароль:   Sweet2026!
```

## Быстрый запуск через Docker Compose

Понадобятся Docker Engine и Docker Compose v2.

```bash
cp .env.example .env
docker compose config --quiet
docker compose up --build -d
docker compose ps
curl --fail http://127.0.0.1:8080/api/health
```

После запуска откройте <http://127.0.0.1:8080>. PostgreSQL и HTTP по умолчанию опубликованы только на loopback-интерфейсе. Для доступа снаружи задайте `APP_BIND=0.0.0.0`, но в production рекомендуется оставить приложение за TLS reverse proxy.

Логи и остановка:

```bash
docker compose logs -f app postgres
docker compose down
```

Именованный volume `postgres_data` сохраняется после `down`. Команда `docker compose down -v` необратимо удалит локальную базу и потребует повторной инициализации.

Перед публичным запуском обязательно замените `POSTGRES_PASSWORD` и ту же часть пароля в `DATABASE_URL`. Спецсимволы в URL-креденшалах должны быть percent-encoded.

## Локальный запуск без Docker

Требуется Go 1.22 или новее.

### Изолированная будущая витрина

Первая frontend-основа находится в `apps/storefront` и запускается отдельно от Go-приложения.
Для неё нужен Node.js 22.12 или новее. Установка и запуск:

```bash
cd apps/storefront
npm ci
npm run dev
```

Новая витрина будет доступна на <http://127.0.0.1:3000>. Она не забирает production-маршрут
`/`: действующий storefront по-прежнему обслуживается Go из `web/` на
<http://127.0.0.1:8080>. В новой витрине подключены маршруты `/` (главная),
`/catalog`, `/categories`, `/categories/:slug`, `/products/:slug`, `/manufacturers`,
`/manufacturers/:slug`, `/collections` и `/collections/:slug`, а также авторизованные
избранное `/favorites`, корзина `/cart`, оформление `/checkout` и подтверждение заказа
`/account/orders/:id`; остальные ссылки новой шапки
указывают на утверждённые будущие канонические маршруты и до следующих миграционных срезов
могут вести на страницу 404.

Чтобы запустить Go API и Next storefront вместе, откройте два терминала из корня репозитория:

```bash
# Терминал 1: действующий Go API с временными демоданными
make run-memory

# Терминал 2: изолированная Next-витрина
cd apps/storefront
cp .env.example .env.local
npm ci
npm run dev
```

После этого реальный демотовар доступен, например, по адресу
<http://127.0.0.1:3000/products/dark-chocolate-sea-salt>. Go остаётся источником названия,
цен, наличия, правил количества, описания, атрибутов и изображений. Next также переписывает
текущие относительные `/assets/*` на настроенный Go origin, чтобы существующие изображения
работали в изолированной локальной разработке.

`STOREFRONT_API_BASE_URL` — server-side origin Go API. В локальной development-среде без
переменной используется `http://127.0.0.1:8080`. Для product и catalog API-запросов в production
переменная обязательна: без неё server-side transport возвращает понятную ошибку и никогда не
обращается к localhost. Сама production-сборка не требует доступного или настроенного backend;
если переменная при сборке отсутствует, `/assets/*` rewrite на localhost не создаётся. Пример
локальной настройки находится в `apps/storefront/.env.example`. Переменная намеренно не имеет
префикса `NEXT_PUBLIC_` и не предназначена для browser-кода. При изменении значения
перезапустите Next dev server.

Структура текущего frontend-среза:

```text
apps/storefront/
  src/app/                 App Router, layout, главная, catalog, discovery и product routes
  src/components/ui/       доступные базовые примитивы
  src/components/storefront/  композиционные элементы витрины
  src/lib/api/             server-side конфигурация, transport и проверка DTO
  src/styles/              семантические tokens и небольшой global foundation
  src/test/                общая настройка компонентных тестов
```

Токены охватывают тёплые нейтральные цвета, типографику, интервалы, радиусы, границы,
ограниченную elevation, motion, responsive-контейнеры, focus, density и z-index. Реализованы
`Button`, `IconButton`, `TextInput`, `SearchInput`, `Badge`, `QuantityControl`, `Container`,
визуально скрытый текст и индикатор загрузки. Сторонняя UI-библиотека не используется.

Проверки frontend:

```bash
cd apps/storefront
npm run typecheck
npm run lint
npm test
npm run build
```

Product route использует текущий `GET /api/products/{product}`, который принимает ID, slug или
регистронезависимый SKU. Канонический Next URL использует возвращённый API slug; обращение по
ID/SKU перенаправляется на него. Запрос выполняется на сервере с `cache: no-store`, потому что
цена и остаток изменяемы. Ответ проверяется на typed boundary; 404 открывает отдельное
not-found состояние, а сетевой/серверный сбой — восстанавливаемое состояние с повтором.

Catalog route использует реальные `GET /api/catalog`, `/api/catalog/facets`, `/api/categories`,
`/api/manufacturers` и `/api/brands`. Состояние хранится в query string: `q`, `category`,
`manufacturer`, `brand`, `series`, повторяемый `tag`, рублёвые границы `min`/`max`, `stock`,
`sale`, `new`, `sort`, `page`, `size` и `view=compact`. UI передаёт цены backend в целых
minor units и использует только серверную пагинацию. Реализованы независимая категория,
цепочка «производитель → бренд → серия», характеристики, цена, наличие, сниженная цена,
новинки, сортировки по названию/дате/цене и размеры страницы 24/48/96. Будущие disjunctive
facet counts не имитируются: текущие facet-значения остаются полностью отфильтрованными.

Каталог имеет два представления: комфортные карточки для просмотра и компактные строки для
работы с большим числом SKU; на узком экране строки перекомпоновываются без горизонтальной
таблицы. Количество на product page остаётся только локальным, а корзина пока отключена.
Избранное работает через существующий Go API для вошедшего пользователя.

Producer navigation использует реальные справочники `GET /api/manufacturers` и `/api/brands`.
`/manufacturers` показывает локально фильтруемый алфавитный список, потому что текущий API
возвращает полный непагинированный справочник. `/manufacturers/:slug` разрешает уникальный slug
(или внутренний ID с перенаправлением на slug), показывает реальные бренды и ведёт в существующий
`/catalog` через точные `manufacturer` и `brand` query-параметры. Серии не загружаются заранее
для каждого бренда: они остаются свободным текстом и появляются как brand-scoped facets уже в
каталоге после выбора бренда. Канонических series routes нет. Отдельные brand pages, server-side
поиск/пагинация производителей и стабильные series entities намеренно отложены до расширения
backend-контракта.

Collection discovery использует реальный непагинированный `GET /api/collections`.
`/collections` показывает только возвращённые API название, описание, изображение и количество,
а `/collections/:slug` разрешает slug или внутренний ID с перенаправлением на канонический slug.
Первые четыре товара загружаются по упорядоченному `productIds` и показываются в редакционном
порядке; полный список открывается в существующем `/catalog?collection=<slug>` с серверной
пагинацией и сортировкой каталога. Пустой справочник и пустая подборка различаются.

Текущая видимость ограничена фактическим контрактом: PostgreSQL и memory показывают подборку,
когда `starts_at` не задан или уже наступил, и `ends_at` не задан или ещё не прошёл; обе границы
включительны. То же расписание применяется к прямому catalog filter, где невидимая или неизвестная
подборка даёт пустой результат. Статусов draft/published/archive нет. Полная lifecycle-модель,
отдельный detail endpoint и catalog-сортировка по редакционному
`collection_products.sort_order` отложены до backend-расширения.

Category navigation использует реальный непагинированный `GET /api/categories`: API возвращает
полный плоский справочник, а дерево строится в storefront по `parentId`. Построение защищено от
повторных ID, неизвестных родителей (становятся корневыми) и циклов (каждая категория выводится
ровно один раз). `/categories` показывает корневые категории с прямыми подкатегориями (не больше
восьми, дальше — ссылка на страницу категории); `/categories/:slug` разрешает slug или внутренний
ID с перенаправлением на канонический slug, показывает хлебные крошки по предкам, подкатегории
или соседние категории и ведёт в существующий `/catalog?category=<slug>`. Собственного списка
товаров у страниц категорий нет. `/catalog` использует то же дерево для активной корневой
категории, отступов в списке и хлебных крошек.

Текущая семантика backend одинакова в PostgreSQL и memory: фильтр `category` и `productCount`
включают саму категорию и только её прямые подкатегории, без рекурсивных потомков. Поэтому
количество подписывается нейтрально («N товаров в каталоге») и совпадает с результатом
нефильтрованного `/catalog?category=<slug>`, а storefront не суммирует счётчики по дереву.
Рекурсивные потомки, защита от циклов и индекс по `parent_id` в базе, detail endpoint категории,
меню каталога в шапке и мобильная навигация по уровням отложены; рекурсия обязательна до
появления таксономии глубже двух уровней.

Глобальный поиск в шапке — доступный combobox поверх существующего `GET /api/search/suggest`.
Браузер обращается к same-origin route handler `apps/storefront/src/app/api/search/suggest`,
который повторяет путь, статусы и конверты Go: запрос короче двух символов даёт `{items: []}`
без обращения к API, длиннее 200 Unicode code points — тот же `422 validation_error`, что и Go;
сбой upstream — `502` с конвертом `internal_error`. Базовый URL API остаётся server-only.
Подсказки запрашиваются с debounce 160 мс, устаревшие запросы отменяются, а поздние ответы
отбрасываются по номеру запроса. Стрелки, Enter, Escape и Tab работают по схеме combobox,
активный вариант объявляется через `aria-activedescendant`, `Ctrl/Cmd+K` фокусирует видимое
поле. Enter без выбранного варианта и последний пункт ведут на канонический `/catalog?q=…`;
`/search?q=…` временно (307) перенаправляет туда же. Без JavaScript форма отправляется в `/catalog`.

Подсказки показывают только то, что возвращает backend: товары, затем категории, производители
и бренды, если после товаров осталось место из восьми. Серий, подборок, артикула и цены в
подсказках нет; бренд ведёт в `/catalog?brand=<slug>`, потому что brand route отсутствует.
Ранжирования по релевантности нет: сортировка результатов с `q` совпадает с обычной сортировкой
каталога (в PostgreSQL последним ключом добавлен `p.id` для детерминированных страниц). Поиск
не нормализует `ё/е` («темный» не находит «Тёмный»), пунктуацию SKU и морфологию; `%` и `_`
в PostgreSQL сохраняют смысл LIKE-шаблонов. Регистр кириллицы сворачивается только в базе с
UTF-8 `LC_CTYPE`: в кластере интеграционных тестов (`initdb --no-locale`, C ctype) `lower()` и
`simple` full text не меняют регистр кириллицы, поэтому регистронезависимость для русских запросов
там не проверяется. Типизированные квоты подсказок, серии/подборки, релевантность, опечатки,
отдельная страница `/search`, полноэкранный мобильный поиск и недавние запросы отложены.

Главная (`apps/storefront/src/app/(home)`) — server-rendered маршрут без собственного client
state. Она строится только из текущих API и не больше чем из семи backend-запросов: параллельно
`GET /api/categories`, `/api/collections` и `/api/manufacturers`, затем параллельно до четырёх
`GET /api/products/{id}` для выбранной подборки. Каталог целиком, facets и brands не
загружаются. Разделы сверху вниз:

- вступление: фактический заголовок и одна фраза о поиске по названию, артикулу, производителю и
  бренду, ссылка «Открыть каталог», ссылка на выбранную подборку (если есть) и декоративная
  фотография `/assets/hero-confectionery.webp` из legacy-ассетов через существующий rewrite;
- категории: корневые категории в порядке ответа API, не больше восьми, с нейтральным счётчиком
  «N товаров в каталоге» и ссылками на `/categories/:slug`;
- подборка: первая подборка **в порядке текущего ответа** `/api/collections`, у которой есть хотя
  бы один `productId`. Видимость по расписанию уже применена в Go; Next не проверяет даты и не
  сортирует подборки. Это правило главной, а не гарантия API: PostgreSQL сейчас сортирует по
  `sort_order, name`, memory — в порядке фикстур. Показываются первые четыре товара в порядке
  `productIds` (тот же код, что у `/collections/:slug`), ссылки на ещё до трёх подборок и на
  `/collections`;
- производители: до восьми производителей с товарами по алфавиту (как в `/manufacturers`, латиница
  перед кириллицей), с ссылками на `/manufacturers/:slug`;
- навигация по разделам: каталог, категории, производители, подборки.

Разделы независимы (`Promise.allSettled`): сбой или пустой ответ убирает только свой раздел;
товар подборки, вернувший ошибку, убирает раздел подборки. Если недоступны все три источника,
остаются вступление, поиск в шапке, ссылки и короткое сообщение `role="status"`. Фикстуры и
заглушки не подставляются. Пустое или не загрузившееся изображение товара (в том числе упавшее
до гидратации) заменяется нейтральным полем «Нет фото» во всех карточках витрины. У backend нет документированных сигналов популярности, «избранных» или
рекомендованных товаров: `sort=popular` — эвристика (`featured`, отзывы, рейтинг), поэтому
главная ничего не называет популярным, рекомендованным или хитом. Редакционные бейджи товаров и
названия подборок из API выводятся дословно, но никогда не используются для отбора. Отложены:
разделы новинок (`newOnly`) и скидок, рекомендации и персонализация, блок повторного заказа,
промо/CMS-контент и изображения подборок, изображения категорий и логотипы производителей,
глобальный footer с подтверждёнными контактами, фильтр каталога по `ids` (сократил бы четыре
запроса товаров до одного), кеширование главной и пагинированные справочники.

### Избранное в Next storefront

`/favorites` показывает реальные сохранённые товары вошедшего пользователя. Один ленивый
client provider обслуживает карточки главной, каталога (оба вида), подборок, страницу товара
и само избранное. Шапка содержит ссылки на desktop и mobile без глобального счётчика и не
загружает избранное ради навигации. Гостевое избранное, browser storage и merge-on-login
в этом срезе не реализованы; намерение добавить товар после входа не сохраняется и не повторяется.

Go владеет HttpOnly cookie-сессией. Браузер сначала вызывает same-origin `GET /api/auth/session`,
затем, только при подтверждённом входе, `GET /api/favorites`. Проверку сессии избранное и корзина
делят через общий browser-session слой (статус, ID пользователя, CSRF в памяти, поколение);
снимки, мутации и сообщения каждой функции остаются отдельными. CSRF передаётся
в `X-CSRF-Token` для изменений; cookie и CSRF не попадают в server-rendered props.
В development `/api/*` использует существующий fallback rewrite, в production маршрутизацию
в Go обеспечивает внешний edge. Ошибка проверки сессии отображается как недоступность,
а не как выход. Каждый снимок избранного привязан к ID пользователя; смена пользователя,
выход или недоступность проверки скрывает прежние приватные данные и инвалидирует поздние ответы.

Изменения не оптимистические: сердечко и список меняются после ответа Go. На весь provider
допускается одна мутация, её полный ответ заменяет снимок. `401` завершает локальное состояние
входа. `403 csrf_failed` вызывает проверку сессии и перечитывание списка без повтора мутации.
После сетевой ошибки, `5xx` или повреждённого успешного ответа выполняется только GET-сверка:
запись могла успеть сохраниться. При неудачной сверке дальнейшие изменения блокируются до
восстановления. Возврат к скрытой/восстановленной вкладке вызывает ограниченную проверку;
синхронизации вкладок в реальном времени нет.

Для перехода на существующий legacy-вход используется отдельная server-only переменная
`STOREFRONT_LEGACY_LOGIN_URL` (без `NEXT_PUBLIC_`). Явное значение должно быть абсолютным
HTTP(S) URL без credentials; неверная конфигурация отклоняется. При отсутствии в development
используется `http://127.0.0.1:8080/#/login`, в production — `null`: сборка проходит, а UI
объясняет необходимость входа без неработающей ссылки. URL не выводится из
`STOREFRONT_API_BASE_URL`; в browser props передаётся только проверенный navigation href.
Переход выполняется обычной ссылкой с полной загрузкой документа. После входа нужно вернуться
в Next самостоятельно: `returnTo` не реализован. При локальной работе используйте одинаковый
hostname для Go и Next (например, `127.0.0.1`), чтобы host-only cookie была общей.

Первый mount товарных controls (избранное и корзина вместе) делает один session GET для гостя
или три GET для вошедшего пользователя (session, favorites, cart) независимо от числа карточек.
Прямой авторизованный `/favorites` делает server session GET, browser session GET и favorites GET,
а при непустом списке карточки добавляют один cart GET; анонимный маршрут без cookie не обращается
к Go. Прямой авторизованный `/cart` — server session GET, browser session GET и cart GET.
Обычная успешная мутация — один запрос; CSRF recovery — ещё session GET и, при входе, favorites
GET; сверка неопределённого результата — один favorites GET. Данные товаров берутся из полного
`items` ответа избранного, без отдельных product/category/manufacturer-запросов. Наличие не
ограничивает сохранение. API пока непагинированный, дублирует товары в `groups` и не имеет
revision; bounded reads, batch actions, guest merge и полная миграция больших списков отложены.

### Корзина в Next storefront

`/cart` и кнопки покупки в карточках (главная, каталог в обоих видах, подборки, избранное) и на
странице товара работают только для вошедшего пользователя. Гостевой корзины, browser storage,
переноса legacy `sloy:cart` и merge после входа нет; намерение купить до входа не сохраняется.
Отдельный ленивый provider корзины использует общий browser-session слой. Шапка ведёт на `/cart`
без счётчика и не загружает корзину. Маршрут проверяет сессию через `getServerSession()` и
передаёт в браузер только статус и ID пользователя; гость видит предложение войти, сбой проверки —
состояние недоступности, а не пустую корзину. Страница закрыта от индексации.

Каждый защищённый ответ Go содержит `X-Authenticated-User-ID` — ID пользователя, авторизовавшего
именно этот запрос (ставится после аутентификации и CSRF до вызова обработчика, отсутствует
у `401` и `403 csrf_failed`, входящее значение игнорируется). Избранное и корзина принимают
приватный ответ, только если заголовок совпадает с ожидаемым пользователем запроса, а пользователь
и поколение запроса — с текущей сессией. Отсутствующий или чужой владелец: ответ отбрасывается,
приватные данные скрываются, выполняется одна общая проверка сессии без повтора мутации;
повторное несовпадение переводит состояние в «недоступно» до явной повторной загрузки.

Изменения не оптимистические, а Go — источник истины для сумм позиций, групп и итогов:
витрина их не пересчитывает и отклоняет небезопасные целые числа. Карточка добавляет
минимальное количество, страница товара — выбранное; `POST` и `PATCH` задают абсолютное
количество (не прибавку), `0` никогда не удаляет. Количество редактируется как черновик:
запись — по Enter, «Применить» или +/−, Escape возвращает подтверждённое значение. На весь
provider допускается одна запись: ответы содержат всю корзину без revision, поэтому параллельные
изменения даже разных товаров и скрытая очередь запрещены. Выбор всей корзины всегда отправляет
`PATCH /api/cart/selection` с явным непустым списком всех канонических ID (локальный поиск и
свёрнутые группы его не сужают); пустая корзина не отправляет запросов. Удаление — только
`DELETE /api/cart/items/{product}`; массового удаления нет. `409` сохраняет введённое количество
и перечитывает корзину, `422` сохраняет черновик без перечитывания, `401` скрывает корзину и
избранное, `403 csrf_failed` проверяет сессию и перечитывает данные без повтора. После сетевой
ошибки, `5xx`, повреждённого ответа или неожиданного статуса показывается последний
подтверждённый снимок с пометкой сверки и выполняется только `GET /api/cart`; при неудаче
изменения блокируются до явной повторной загрузки. Порядок позиций — порядок ответа Go
(не «недавние»); `updatedAt` не используется как revision.

Отложены: гостевая корзина и merge, история заказов, счётчик в шапке, массовое удаление,
undo, фильтры выбранного/проблем, перенос в избранное, плотности, виртуализация и пагинация.

### Оформление заказа в Next storefront

`/checkout` доступен только вошедшему пользователю и открывается ссылкой «Перейти к оформлению» из
корзины, если выбрана хотя бы одна позиция и у выбранных нет проблем наличия. Ссылка ничего не
записывает. Маршрут, как и `/cart`, проверяет сессию на сервере и при входе заново читает корзину;
отдельного выбора для заказа нет — показываются только выбранные строки корзины, их цены и итоги Go
(«Товары без скидки», «Скидка», «Доставка», «Итого») и число невыбранных позиций, которые останутся в
корзине. Форма содержит только адрес доставки (обязателен) и необязательный комментарий, без
придуманных ограничений длины; имени, телефона, оплаты и интервала доставки нет.

Подтверждение — один `POST /api/orders` с `Idempotency-Key` (`crypto.randomUUID()`), CSRF,
`X-Expected-Authenticated-User-ID` и обзором (`expectedItems`, `expectedTotalMinor`), скопированным из
того же снимка корзины. Запрос держит общую блокировку записи корзины, таймаут — 20 секунд, повторов
нет. `409 checkout_changed`, `out_of_stock` и `conflict` перечитывают корзину, сохраняют форму, текстом
отмечают изменившиеся цены, количество и состав и требуют нового подтверждения с новым ключом; `422`
показывает ошибки полей; `403 csrf_failed` проверяет сессию и перечитывает корзину без повтора; `401`
завершает вход; чужой владелец ответа или `authenticated_user_changed` отбрасывают попытку.
При сетевой ошибке, таймауте, `5xx` или повреждённом `201` результат считается неизвестным: форма
блокируется, корзина не используется как доказательство, а кнопка «Проверить заказ» по явному
действию отправляет тот же запрос с тем же ключом — Go вернёт уже созданный заказ
(`Idempotent-Replayed`) или выполнит его один раз. Незавершённая попытка не сохраняется в браузере.

После `201` витрина переходит (`router.replace`) на `/account/orders/:id`. Страница читает
`GET /api/orders/{id}` с проверкой владельца и показывает номер, дату, статус Go, адрес, комментарий,
снимки позиций и «Итого с доставкой» — разбивки суммы у заказа в API нет. Плашка «Заказ … оформлен»
появляется только сразу после оформления в этой вкладке; после перезагрузки остаётся сам заказ.
Ссылки на товары используют ID из снимка (удалённый товар откроет 404). Каждый приватный запрос
браузера передаёт `X-Expected-Authenticated-User-ID`, поэтому Go отклоняет запрос устаревшей вкладки до
любых изменений. История заказов, повтор заказа, гостевое оформление, оплата и отмена отложены.

Пока не реализованы страницы брендов/серий, аккаунт, история заказов, администрирование и
production route ownership.

### In-memory demo mode

```bash
make run-memory
```

Или явно:

```bash
APP_MODE=demo DATABASE_URL= \
WEB_DIR=web \
MIGRATIONS_DIR=migrations \
go run ./cmd/server
```

Memory repository включается при пустом `DATABASE_URL` только с явным `APP_MODE=demo` или `APP_MODE=development`. По умолчанию действует `APP_MODE=production`: без PostgreSQL DSN сервер завершает запуск с ошибкой. Это удобный режим для интерфейса, API и тестирования сценариев, но все корзины, сессии и заказы исчезают при перезапуске процесса. Для нескольких реплик и любых сохраняемых данных он не подходит.

### PostgreSQL mode

Можно поднять только базу из Compose и запустить Go-процесс на хосте:

```bash
cp .env.example .env
docker compose up -d postgres

DATABASE_URL='postgres://sweetshop:LOCAL_PASSWORD@127.0.0.1:5432/sweetshop?sslmode=disable' \
RUN_MIGRATIONS=true \
WEB_DIR=web \
MIGRATIONS_DIR=migrations \
make run-postgres
```

Замените `LOCAL_PASSWORD` значением из вашего локального `.env`. Для подключения с хоста используйте `POSTGRES_PORT` (в `.env.example` и примере выше — 5432), а внутри Compose — `postgres:5432`.

При первом старте приложение создаст `schema_migrations`, применит все `*.up.sql` по имени и загрузит демоданные. Каждая миграция выполняется транзакционно и повторно не применяется. Для нескольких production-реплик миграции следует запускать ровно одним экземпляром приложения, а на остальных задавать `RUN_MIGRATIONS=false`.

## Конфигурация backend

Сервер читает переменные окружения напрямую; `.env` автоматически обрабатывает Docker Compose, но не команда `go run`.

| Переменная | Значение по умолчанию | Назначение |
|---|---:|---|
| `APP_MODE` | `production` | `production`, `development` или `demo`. Только два последних допускают memory repository без DSN. |
| `DATABASE_URL` | пусто | PostgreSQL DSN. Обязателен в production; ошибочный или недоступный DSN никогда не вызывает переход в memory. |
| `RUN_MIGRATIONS` | `true` | Автомиграции PostgreSQL; отключаются только точным значением `false`. |
| `WEB_DIR` | `web` | Каталог статического frontend. В образе — `/app/web`. |
| `MIGRATIONS_DIR` | `migrations` | Каталог SQL-миграций. В образе — `/app/migrations`. |
| `HTTP_ADDR` | `:$PORT` | Полный адрес HTTP listener; имеет приоритет над `PORT`. |
| `PORT` | `8080` | Порт, если `HTTP_ADDR` не задан. |
| `DB_MAX_CONNS` | `max(4, CPU)` | Максимальный размер пула PostgreSQL. |
| `DB_MIN_CONNS` | `1` | Минимальный размер пула PostgreSQL. |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` или `error`. |

Проверка готовности:

```bash
curl --fail http://127.0.0.1:8080/api/health
```

Ответ содержит `status`, UTC-время и активное хранилище (`memory` либо `postgres`).

## API

Машиночитаемый контракт: [api/openapi.yaml](api/openapi.yaml). Ограничения, отличия адаптеров и результаты baseline-проверок: [docs/baseline.md](docs/baseline.md).

Все ответы — JSON, денежные значения с суффиксом `Minor` передаются целым числом в копейках. Защищённым маршрутам нужен заголовок `Authorization: Bearer <token>` (или cookie-сессия браузера с CSRF для изменений); их успешные и прикладные ошибочные ответы содержат `X-Authenticated-User-ID`. Сессия действует 30 дней; в базе хранится SHA-256-хэш, а не сам bearer token. Необязательный заголовок `X-Expected-Authenticated-User-ID` — предусловие, а не авторизация: если он передан, Go после аутентификации и до обработчика сверяет его с ID вошедшего пользователя и при несовпадении, пустом или повторённом значении отвечает `409 authenticated_user_changed` без каких-либо изменений.

### Повтор заказа

Сначала frontend вызывает preview. Для демозаказа в PostgreSQL:

```bash
curl --fail --request POST \
  --header "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8080/api/orders/ord-2026-002/repeat/preview
```

Ответ показывает для каждой позиции заказанное, доступное и уже находящееся в корзине количество, текущую цену, статус `available`, `limited`, `unavailable` или `discontinued`, а также возможную замену. После редактирования отправляется точный выбор пользователя:

```bash
curl --fail --request POST \
  --header "Authorization: Bearer $TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"items":[
    {"productId":"p01","quantity":2,"selected":true},
    {"productId":"p07","quantity":4,"selected":true},
    {"productId":"p18","quantity":0,"selected":false}
  ]}' \
  http://127.0.0.1:8080/api/orders/ord-2026-002/repeat/commit
```

Backend заново строит preview перед commit, валидирует актуальный остаток, минимальное количество и шаг, затем применяет все изменения корзины одной операцией repository. Если `items` отсутствует, равен `null` или пуст, используются предложенные количества из нового preview. Это текущий legacy-контракт: обязательного предварительного review, фиксации цены и идемпотентности нет.

### Оформление заказа: идемпотентность и проверка

`POST /api/orders` без новых полей работает как раньше и не идемпотентен. Новый клиент передаёт
заголовок `Idempotency-Key` (16–128 символов `A-Za-z0-9_-`, например `crypto.randomUUID()`) и
подтверждённый обзор: `expectedItems` (`productId`, `quantity`, `unitPriceMinor` выбранных строк) вместе
с `expectedTotalMinor`. Go в той же транзакции после блокировок сверяет точный набор выбранных строк,
количества, текущие цены и итог с доставкой; при расхождении — `409 checkout_changed` без записей.
Эти значения только сравниваются и никогда не определяют цену заказа.

Ключ и вычисленный сервером SHA-256-дайджест нормализованного запроса хранятся в созданном заказе
(уникальны в пределах пользователя). Повтор с тем же ключом и тем же запросом возвращает исходный заказ
с `201` и `Idempotent-Replayed: true` — даже когда корзина уже израсходована; тот же ключ с другим
запросом — `409 idempotency_key_reused`. Неудачные попытки ничего не сохраняют. Проверка минимального
количества и шага при оформлении по-прежнему не выполняется.

## Чистая архитектура

```text
cmd/server/                    composition root, конфигурация, HTTP lifecycle
internal/domain/               сущности, ошибки и интерфейс Repository
internal/application/          use cases и бизнес-валидация
internal/delivery/httpapi/     HTTP-маршруты, auth, JSON, middleware
internal/repository/memory/    временный демо-адаптер
internal/repository/postgres/  production-адаптер и runner миграций
migrations/                    версионированная схема и seed
web/                           статический frontend
```

Домен и application-слой не зависят от HTTP или PostgreSQL. `cmd/server` проверяет `APP_MODE`, выбирает adapter по наличию `DATABASE_URL` и связывает зависимости через интерфейс `domain.Repository`.

Каталог моделируется двумя дополняющими осями: дерево товарных категорий отвечает на вопрос «что это», а цепочка «производитель → бренд → серия → товар» — «кто и в какой линейке это выпустил». Подборки остаются независимыми many-to-many наборами товаров, поэтому навигация не разрастается в дублирующее дерево.

## Production checklist

`APP_MODE=production` закрывает только опасный fallback без базы. Миграция `002` по-прежнему добавляет демоаккаунт даже в production; этот этап не делает приложение готовым к публичным продажам. Если отслеживаемый ранее `.env` использовался в развёртывании, соответствующие учётные данные необходимо ротировать. Удаление из индекса не удаляет секреты из истории Git.

- замените демонстрационный пароль PostgreSQL и при необходимости удалите/заблокируйте `demo@sugar.ru` отдельной production-миграцией;
- передавайте секреты через secret manager платформы, не коммитьте `.env`;
- завершайте TLS на reverse proxy/load balancer, задайте ограничения request body и rate limits на внешнем контуре;
- не публикуйте порт PostgreSQL наружу; loopback-bind в Compose предназначен только для администрирования одного хоста;
- включите регулярные backup/PITR, мониторинг пула, диска и latency, а JSON-логи направьте в централизованное хранилище;
- запускайте миграции одним release-job/экземпляром, после чего выставляйте `RUN_MIGRATIONS=false` на остальных репликах;
- используйте PostgreSQL для нескольких реплик: memory mode неперсистентен и изолирован внутри процесса;
- проверяйте `/api/health` readiness-пробой и давайте процессу до 10 секунд на graceful shutdown;
- образ уже запускается без root, а Compose дополнительно включает read-only root filesystem, `no-new-privileges` и удаляет Linux capabilities.
